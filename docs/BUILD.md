# Сборка и сопровождение

[← README](../README.md)

Для использования готовых наборов достаточно примера из README. Эта страница описывает проверку релизов, локальную сборку и обслуживание собственного форка.

## Как формируются наборы

Источники и пределы их размеров заданы в [sources.json](../config/sources.json). Каждый обязательный источник скачивается по HTTPS; URL, время получения и SHA-256 записываются в manifest.

Домены нормализуются через IDNA2008/UTS46. Точные `domain` остаются точными; `domain_suffix` охватывают сам домен и его поддомены. Политика фильтрует общие зоны и платформы до объединения. Удаление общей записи, например `googleapis.com`, сохраняет явно перечисленные дочерние домены.

Public Suffix List используется для фильтрации широких правил. Отдельные домены сервисов из секции PRIVATE сохраняются, если явно перечислены в `service_owned_suffixes` и присутствуют в источниках. Сам по себе этот параметр домены не добавляет. PRIVATE wildcard не используется для удаления доменов отдельных арендаторов.

После объединения удаляются только дубли и условия, покрытые уже существующим суффиксом. Сам сборщик новые родительские домены не создаёт, но новый внешний suffix может поглотить более узкие записи. Поэтому `domain-changes.json` содержит не только добавленные/удалённые строки, но и `effective_added`/`effective_removed` — изменения с учётом фактического совпадения правил.

[probes.json](../config/probes.json) содержит два слоя:

- `domains` — наблюдения для отчёта;
- `expectations` — обязательные решения `VPN` или `Direct` после Direct-исключений. Несовпадение останавливает сборку.

### Ручные включения и исключения

[manual-vpn.json](../config/manual-vpn.json) добавляет проектные VPN-правила, [direct-exceptions.json](../config/direct-exceptions.json) формирует отдельный приоритетный набор Direct. Пример:

```json
{
  "schema_version": 1,
  "rules": [
    {
      "kind": "domain_suffix",
      "domain": "service.example",
      "reason": "Issue #123: подтверждённый недоступный сервис",
      "review_after": "2027-02-01"
    }
  ]
}
```

Поля `kind`, `domain` и `reason` обязательны для обоих файлов, `review_after` обязателен для Direct-исключений. Допускаются `domain` и `domain_suffix`; public suffixes запрещены. Ручное правило для общей инфраструктуры должно иметь явное обоснование. Дубликаты запрещены. Личные правила конкретного роутера в репозиторий не добавляются.

### IP-наборы

Сервисные сети собираются по [service-networks.json](../config/service-networks.json): официальный CIDR-список Telegram и снимки BGP-маршрутов пяти выделенных AS Telegram из RIPE RIS. Проверяются идентификатор AS, оператор, свежесть, публичность, границы и фактическое адресное покрытие. Транзитные и общие облачные сети не включаются.

`blocked-registry-ip.srs` формируется иначе: из уже подключённых текстовых блок-листов извлекаются только публичные отдельные IP. Они становятся `/32` или `/128`, без расширения до соседних сетей. Неверные записи классифицируются в manifest по причинам; валидные IP больше не смешиваются с malformed-доменами. Изменение адресов сравнивается с предыдущим набором, а не только с количеством строк.

`routing-direct-exceptions.srs` может быть пустым: это безопасный набор без совпадений, а не match-all правило.

Все IP-наборы предназначены только для маршрутизации. В DNS используется исключительно `blocked-domains.srs`. DNS-resolve миллионов доменов в IP, облачные ASN, CDN и составные широкие списки автоматически не импортируются. Пределы охвата описаны в [IP-COVERAGE.md](IP-COVERAGE.md).

Известные ограничения источников: `unavailable-in-russia` пополняется накопительно и не гарантирует своевременное удаление записей. Antifilter full уже включает community и Re-filter. Причину конкретного совпадения следует смотреть в отчёте конкретного релиза, а ложное срабатывание оформлять пересматриваемым Direct-исключением.

## Проверка релиза

В [Releases](https://github.com/Vanilla-SilQ-HD/Routing/releases) публикуются:

| Файл | Назначение |
| --- | --- |
| `blocked-domains.srs` | Домены для маршрутизации и DNS |
| `blocked-services-ip.srs` | Проверенные сети приложений |
| `blocked-registry-ip.srs` | Точные `/32` и `/128` из блок-листов |
| `routing-direct-exceptions.srs` | Приоритетные Direct-исключения |
| `<имя>.srs.sha256` | SHA-256 соответствующего набора |
| `<имя>.json.gz` | Сжатый исходник правил |
| `manifest.json` | Источники, хеши, размеры и результаты проверок |
| `domain-changes.json` | Семантический diff и выборки изменений |
| `manual-rules.json` | Опубликованные ручные правила и их причины |
| `report.html`, `probes.json`, `excluded.json` | Отчёт, маршруты probes и исключённые широкие записи |
| `release.json`, `SHA256SUMS` | Идентификатор сборки и хеши всех вложений |

Для проверки пары «файл + хеш» сначала фиксируйте тег релиза: между двумя обращениями к `latest` может выйти новая версия.

```powershell
$release = Invoke-RestMethod 'https://api.github.com/repos/Vanilla-SilQ-HD/Routing/releases/latest'
$base = "https://github.com/Vanilla-SilQ-HD/Routing/releases/download/$($release.tag_name)"
Invoke-WebRequest "$base/blocked-domains.srs" -OutFile blocked-domains.srs
Invoke-WebRequest "$base/blocked-domains.srs.sha256" -OutFile blocked-domains.srs.sha256
$expected = (Get-Content blocked-domains.srs.sha256).Split(' ')[0]
if ((Get-FileHash blocked-domains.srs -Algorithm SHA256).Hash -ne $expected) { throw 'SHA-256 mismatch' }
```

Для фиксации или отката используйте URL конкретного тега: `releases/download/<tag>/blocked-domains.srs`. Автоматика не перезаписывает и не удаляет опубликованные релизы.

## Локальная сборка

Нужен Python 3.11+; CI использует Python 3.13. Установщик закреплённого компилятора поддерживает Windows и Linux x64. Версия sing-box и SHA-256 официальных архивов зафиксированы в [tools-lock.json](../config/tools-lock.json). Сейчас используется sing-box 1.14.4 и формат исходного rule-set v3.

Windows PowerShell, из корня репозитория:

```powershell
python -m venv .venv
& ./.venv/Scripts/python.exe -m pip install --require-hashes -r requirements.txt
& ./.venv/Scripts/python.exe -m unittest discover -s tests -v
& ./.venv/Scripts/python.exe scripts/install_tools.py
& ./.venv/Scripts/python.exe scripts/build.py --output dist/first
```

Linux:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements.txt
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python scripts/install_tools.py
.venv/bin/python scripts/build.py --output dist/first
```

Повторная проверка из кеша без скачивания источников:

```powershell
& ./.venv/Scripts/python.exe scripts/build.py --offline `
  --previous dist/first/manifest.json `
  --previous-rules dist/first/blocked-domains.json `
  --output dist/replay
```

Каталог результата должен быть новым или пустым. Сборщик компилирует все четыре набора, декодирует их обратно, сравнивает условия и выполняет `sing-box check`. Сетевой сервис при этом не запускается. Готовый каталог появляется только после всех проверок; неудачная сборка не перезаписывает предыдущий результат. Локальные сборки автоматически не публикуются.

### Измерение памяти

`measure_memory.py` запускает sing-box без inbound, загружает указанные локальные SRS и измеряет максимальный RSS процесса:

```powershell
& ./.venv/Scripts/python.exe scripts/measure_memory.py --seconds 5 `
  dist/first/blocked-domains.srs `
  dist/first/blocked-services-ip.srs `
  dist/first/blocked-registry-ip.srs `
  dist/first/routing-direct-exceptions.srs
```

Это измерение на текущей машине, а не гарантия для Keenetic. На роутере дополнительно проверьте свободную память, время старта и стабильность под нагрузкой.

## GitHub Actions и собственный форк

Основная ветка workflow — `main`. В форке включите Actions и запустите **Build selective VPN rule sets → Run workflow**. Первому релизу не требуется предыдущая база сравнения. Публикация использует `GITHUB_REPOSITORY`, поэтому файлы попадут в Releases форка; ссылки в его README нужно заменить на свои.

Расписание: `35 0,6,12,18 * * *` UTC. Запуск также доступен вручную и при изменениях сборщика, настроек или тестов. GitHub может задерживать расписание и отключать его в публичном репозитории после длительного отсутствия активности.

Сборочный job имеет права чтения. Отдельный job публикации получает `contents: write` только после его успеха. Используется встроенный `GITHUB_TOKEN`; личный токен не нужен.

Публикация сначала создаёт черновик `rules-<run_id>-<attempt>`, загружает все вложения и проверяет их обратным скачиванием. Только затем релиз становится публичным и назначается Latest. При одинаковых SRS и рецепте новый релиз не создаётся, а текущие бинарные файлы повторно проверяются. Изменение любого набора требует нового релиза.

Артефакт `selective-vpn-rules` содержит полный результат и снимки источников; срок хранения — 2 дня. `rules-manifest` хранится 90 дней. Дополнительно `load_baseline.py` восстанавливает предыдущий `blocked-domains.json` из последнего опубликованного релиза для семантического diff.

## Если сборка остановилась

Ошибка обязательного доменного источника, неожиданная структура данных, несовпадение обязательного probe или повреждённый файл останавливают публикацию. Падение числа доменных условий более чем на 20%, рост более чем на 50%, смена состава источников или база старше 7 дней требуют проверки. Для сервисных и registry IP отдельно контролируется фактическое адресное покрытие.

При сбое только сервисного источника допускается восстановление **полного** набора из предыдущего manifest не старше 24 часов. В report и manifest фиксируются `previous-service-data-stale`, исходное время и ошибки скачивания. Если предыдущего полного набора нет, он устарел, изменился состав/URL источников или данные не проходят текущие ограничения, сборка останавливается. Частичный IP-набор и offline-replay с отсутствующими входами не допускаются.

Сначала посмотрите причину в Actions и сравните источники с последним manifest. Если изменение намеренное и проверено, запустите workflow вручную с `reset_baseline=true`. Он формирует новую базу сравнения; отсутствие предыдущей базы допускается только для первого релиза или такого явного сброса. Остальные предупреждения продолжают блокировать публикацию.

Пока сборка не исправлена, постоянная ссылка отдаёт последний успешный релиз. Его доступность не означает, что данные продолжают обновляться.
