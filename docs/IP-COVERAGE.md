# IP-наборы: источники и охват

[← README](../README.md)

Проект разделяет два разных типа IP-правил:

- `blocked-services-ip.srs` — консервативно проверенные сети конкретных приложений, сейчас Telegram;
- `blocked-registry-ip.srs` — отдельные публичные адреса `/32` и `/128`, уже присутствующие в подключённых блок-листах.

Оба набора используются только в маршрутизации, не в DNS. Direct-исключения располагаются выше них, остальной трафик идёт напрямую.

## Почему нельзя просто получить IP всех доменов

Домен и IP не имеют однозначного соответствия. На одном адресе CDN могут работать заблокированный сайт и множество доступных сервисов. DNS-ответы меняются по времени и региону, а доменный суффикс охватывает поддомены, которые нельзя перечислить одним DNS-запросом. Приложение также может получать адрес сервера внутри собственного протокола, без DNS.

Массовое разрешение доменного списка в IP изменило бы правило: вместо конкретного сайта в VPN попадали бы все соединения к его общему адресу. Поэтому домены остаются доменами, а IP добавляются только из отдельно разобранных источников.

## Точные адреса из блок-листов

Текстовые доменные источники иногда содержат и отдельные IP. Раньше такие строки отбрасывались вместе с malformed-записями. Теперь они извлекаются в `blocked-registry-ip.srs` с сохранением источника и статистики:

- публичный IPv4 становится `/32`, публичный IPv6 — `/128`;
- адрес не расширяется до соседней сети;
- приватные, специальные и malformed-записи не включаются;
- дубли удаляются, изменение покрытия сравнивается с предыдущим релизом.

На момент проверки актуальных источников найдено **10 уникальных публичных IPv4**: 2 в Antifilter full и 8 в Re-filter. Количество может меняться с upstream.

Этот набор намеренно отделён от сервисных сетей. Наличие адреса в блок-листе не доказывает выделенность: IP может быть общим у нескольких ресурсов. Если набор захватывает нужный прямой ресурс, его можно отключить независимо от Telegram или переопределить более приоритетным Direct-правилом.

## Telegram

Обязательные источники:

- [Официальный CIDR-список Telegram](https://core.telegram.org/resources/cidr.txt): IPv4 и IPv6.
- [RIPE RIS / RIPEstat](https://stat.ripe.net/docs/data-api/api-endpoints/ris-prefixes): сети с `AS44907`, `AS59930`, `AS62014`, `AS62041`, `AS211157` как источниками BGP-маршрута. Транзитные сети не включаются. Идентичность оператора проверяется отдельным ответом [AS Overview](https://stat.ripe.net/docs/data-api/api-endpoints/as-overview).

На **6 ноября 2026 года** объединение этих AS добавляет к официальному списку `95.161.64.0/20`. [RIPE RIS](https://stat.ripe.net/data/ris-prefixes/data.json?resource=AS62041&list_prefixes=true&types=o) видит его анонс от `AS62041`; [маршрутный объект RIPE](https://rest.db.ripe.net/search.json?query-string=95.161.64.0%2F20&type-filter=route) указывает `TM Subnets` и `AS62041`. [RDAP](https://rdap.db.ripe.net/ip/95.161.64.0) содержит имя сети `TM-SUBNETS` и контакт Telegram Messenger Inc, а регистрантом указывает Global Network Management Inc. Это подтверждение использования диапазона Telegram, а не утверждение о владении адресами.

Сборка проверяет имя оператора и номер AS, свежесть снимка, структуру ответа и границы сетей. Снимки и хеши сохраняются. Это помогает учитывать новые анонсы выбранных AS без ручного добавления адресов; смена оператора или неожиданное расширение требует проверки.

Если один из сервисных источников временно недоступен, сборка может использовать только **полный ранее проверенный набор** из manifest не старше 24 часов. Исходное время и ошибки скачивания публикуются. Частичный набор, устаревший fallback или fallback после изменения состава/URL источников запрещены.

## Пределы покрытия

Даже сервисные сети не покрывают произвольные адреса собеседников в [P2P-звонках Telegram](https://core.telegram.org/api/calls), сторонние прокси и новые серверы вне выбранных источников. Динамические голосовые адреса нельзя одновременно полностью и точно покрыть статическим списком. Списки не проверяют доступность каждого ресурса у конкретного провайдера.

Новые источники можно добавлять после проверки назначения, общих сетей, условий портов/протоколов и поведения обновлений. Широкое правило для всего облака такой проверкой не заменяется.
